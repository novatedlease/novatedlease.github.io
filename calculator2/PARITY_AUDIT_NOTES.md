# Headline-figure parity audit (item 11) — findings

Verification-only pass; no source files were modified. Built both apps unmodified
(`calculator/` and `calculator2/`), served both via `vite preview`, and compared
rendered output with a headless Chromium (Playwright, driven from a scratch script,
not committed anywhere in the repo).

## Finding 1 (critical, blocks all custom-scenario comparison): share links are NOT actually bidirectionally compatible between v1 and v2

- `calculator2/` imports `encodeInputsToUrlParam`/`getInputsFromLocationSearch` from
  `calculator/src/engine/urlState.ts`. That file's payload shape is `{ v: 1, i: {...} }`
  (see `UrlPayloadV1` in that file).
- `calculator/src/App.tsx` (the live v1 app) does **not** import `engine/urlState.ts` at
  all (confirmed: zero references to it anywhere under `calculator/src/` other than the
  file itself). It has its own inline, separately-defined `encodeInputsToUrlParam` /
  `readInputsFromUrl` / `toBase64Url` / `fromBase64Url` (App.tsx lines ~180-317), whose
  payload shape is `{ v: 1, inputs: {...} }` — a different key (`inputs` vs `i`).
- Net effect: a `?c=` link generated by v2 decodes to `parsed.inputs === undefined` in
  v1's decoder (since the real key is `i`), fails the `typeof parsed.inputs !== "object"`
  check, and v1 silently falls back to its own defaults — no error, no console warning,
  just silently wrong (defaults) inputs. Verified empirically: fed v2 a custom scenario
  (income $150,000) via `?c=`, loaded the same link in v1, and v1 rendered its default
  $300,000 income figure instead.
- `calculator2/tests/share-link.test.ts` does **not** catch this — its own comment says
  "both import this exact same engine/urlState.ts codec," which is the incorrect premise;
  the test only round-trips the codec against itself, never against v1's actual live
  encoder. So the Phase-1 status line "Share links (?c=, bidirectional v1 compat,
  tested)" is not actually true today — only v2-to-v2 (or hypothetical-v1-if-it-used-the-
  shared-module) round-trips are tested.
- Impact: any user who copies a v1 share link and opens it against v2 (or vice versa)
  during the side-by-side preview period gets silently wrong numbers, not an error.
  This is exactly the kind of bug the working rules warn about (passes tests, wrong at
  runtime).
- Fix sketch (not applied — flagging per scope): either (a) make v1's App.tsx import and
  use `engine/urlState.ts` instead of its inline duplicate (removes the duplication
  entirely — bigger diff to v1, which the phase-2 rules say must stay untouched pixel-
  for-pixel until cut-over), or (b) make v2's codec bilingual — decode both `{v,i}` and
  `{v,inputs}` shapes, and continue encoding as `{v,i}` (or switch to `{v,inputs}` to
  match the live app) — smaller, v2-only change. Recommend (b) given the "never modify
  calculator/src" constraint, but that's an owner call.

This finding also means: every "diff" surfaced by my earlier custom-scenario comparison
pass (5 scenarios built via the engine's own encoder) was actually just "v1 rendering its
defaults vs v2 rendering my custom inputs" — not real per-field bugs. I discarded that
data once I traced the root cause. Real comparisons below use the **default** scenario
(both apps start from the same hardcoded default `Inputs`, confirmed identical value-for-
value in `calculator/src/App.tsx`'s `defaultInputs` vs `calculator2/src/state/defaultInputs.ts`'s
`advancedDefaultInputs` — same numbers, so this is a valid, guaranteed-clean comparison
even though it's only one scenario).

## Finding 2 (confirmed content gap, not a numeric-correctness bug): v2's Section 2 (Financial Summary) is missing v1's Cash-Flow/Asset/Liability breakdown tables

- Default-scenario diff of the **Summary tab**: zero discrepancies both directions —
  every headline "better/worse off by $X" figure, cashflow/interest decomposition number
  matches exactly between v1 and v2.
- Default-scenario diff of the **Details tab**: v1 shows ~14 extra dollar figures v2
  doesn't. All trace back to one place: `calculator/src/components/FinancialReport.tsx`'s
  Section 2 renders a full per-scenario Cash Flow / Asset / Liability row breakdown
  (e.g. "Extra Cash From Sale of Old Car", "Upfront Cost", "= Total", "Car Asset Value",
  "Additional Home Loan Interest Accrued (cf. no car)", each with both an "@ lease end"
  and "@ 5 years" column) — 979 lines total in that file. `calculator2/src/components/
  reports/FinancialSummaryReport.tsx` is an 85-line simplified redesign: a single
  "total spend by pathway" table plus a stat grid. It's a **deliberate redesign
  simplification** per its own doc comment ("presented as a scenario-comparison table
  rather than v1's spreadsheet-style row-by-row layout — a deliberate redesign choice,
  not a different calculation") — the top-line totals it does show (verified above,
  matches exactly) are correct; it just omits the row-by-row cash-flow/asset/liability
  breakdown v1 shows in the same section.
- This is the same kind of content v1's `ComparatorView.tsx` also shows (Section B, per
  item 15 in the phase-2 doc) — but it exists in v1 in **two places**: the per-quote
  Financial Summary section AND the multi-quote Comparator view. Item 15 only scopes
  porting it into `ComparatorView`. This finding flags that the **single-quote** version
  (Section 2) is also missing it, which item 15 doesn't currently cover. Worth a decision:
  is the trimmed-down single-table version an accepted scope cut (nothing here is
  factually wrong, it's just less detail), or should the row-by-row breakdown be ported
  into `FinancialSummaryReport.tsx` too? Recommend treating as a deliberate, acceptable
  simplification given the totals are correct and it was already documented as
  intentional — but flagging since it wasn't in the phase-2 doc's explicit gap list.
- One unconfirmed minor item: v2's BasicInformationReport EV-charging stat shows
  "$449.25" ("Net charging expense (after tax reimbursement)") that didn't have an exact
  counterpart in v1's default-scenario text dump — likely just a different combination/
  labeling of the same underlying charging-delta numbers (which do match), not chased
  further given time budget; worth a quick manual side-by-side glance if the owner wants
  full certainty on this one specific stat.

## Verdict (superseded by the multi-scenario sweep below)

Parity on the one clean (default) scenario checked is solid — Summary tab is byte-for-
byte number-identical, and the one Details-tab gap found is a known, documented, correct-
totals-just-less-detail simplification. But **confidence in "parity checked" for anything
beyond the default scenario is currently unearned** — the mechanism this task was told to
rely on (share links) turned out to be broken, which is itself the most important finding
of this pass and should be fixed (or the multi-scenario sweep redone by hand) before
signing off on general parity.

# Multi-scenario parity sweep (item 11, re-run after the share-link codec fix)

Re-running CALCULATOR2_NOTES.md §5 Prompt A now that `f92be20b` fixed the share-link
payload-key mismatch (`{v,i}` → `{v,inputs}`), which is what blocked custom-scenario
comparison in the pass above. Verification-only; no source files were modified as a
result of this pass (see "Fixes applied" — none were needed).

## Method

Built both apps unmodified (`git diff --stat calculator/` empty throughout), served both
via `vite preview` (v1 on :4501, v2 on :4502), and drove both with headless Chromium
(Playwright, Python sync API, `chrome-mac-arm64/Google Chrome for Testing.app` from the
`ms-playwright/chromium-1217` cache — scripts stayed in the scratchpad, not the repo).

Reused all 30 golden-master scenarios verbatim from `calculator2/tests/golden-master.test.ts`
(FBT category tiers, vehicle-condition/GST/used-EV eligibility, lease term 1-5y, deferral,
luxury adjustment, income bracket edges incl. Div 293 territory, the SG-loss toggle, and
both comparators individually and combined) — encoded each scenario's exact `Inputs` via
the real `encodeInputsToUrlParam` codec into a `?c=` link, and loaded the **same** link in
both apps. For each scenario: Summary tab, Details tab (every section expanded), and for
the 3 comparator-enabled scenarios, the Compare tab (quote saved via the real "save
current" UI flow in each app, then every available pathway checkbox selected). Extracted
all rendered text and diffed every dollar/percentage figure between v1 and v2.

**Methodology pitfall caught and fixed mid-run:** the first pass under-reported real
content in v2 because v2's Details-tab `Section` component (`calculator2/src/components/
ui/Section.tsx`) is a custom button + conditional-render collapsible, not a native
`<details>` element like v1's `CollapsibleSection`. A script that force-opens `<details>`
elements does nothing for v2's sections, so 6 of its 8 Details sections (everything except
"Basic information" and "Section 2: Financial summary", the only two with `defaultOpen`)
never actually rendered their content during automated extraction — producing dozens of
"only in v1" false positives (chart axis labels, ATI/SG rows, etc., all from sections that
were simply never clicked open in v2). Fixed by clicking every collapsed
`button.nlc-section__header[aria-expanded="false"]` before extracting text. This is the
same "collapsed Section renders nothing" trap flagged in CALCULATOR2_NOTES.md §4's working
rules — worth noting for any future automated check of v2's Details tab. For the record:
both apps default to the *same* UX (only 2 of 8 report sections auto-expanded; the rest
need a click) — this is not a v1/v2 discrepancy, just a DOM-mechanism difference that
broke naive automation.

## Findings

**Zero real numeric divergences across all 30 scenarios**, across every area named in the
task: ComparatorView net positions and its cash-flow/asset/liability breakdown rows (both
individually-selected pathways and the combined comparator scenario), all three
EffectiveInterestReport rate definitions, the LeaseReport FY table, the WorstCase
early-termination-risk series, ATI/RFBA rows, and SG rows. Every dollar figure that
appears in one app's rendered output appears in the other, to the cent.

Three residual diffs surfaced by the automated text diff, all confirmed benign
(non-numeric / presentation-only) by tracing their context:

1. **v1-only "M1: X% · M2: Y%" tooltip** on the Residual Value input field — v1 shows both
   ATO minimum-residual reference methods as a percentage pair (varies with lease term,
   e.g. "M1: 28.13% · M2: 30.71%" at 5 years). v2's equivalent field has a simpler hint
   ("Auto-filled from the ATO minimum for your lease term...") without the numbers. The
   residual value **dollar figure itself matches exactly** in every scenario — this is a
   reference-tooltip content simplification, not a calculation difference.
2. **v2-only "~40% of drive-away cost" tooltip** on the Estimated Market Value field — a
   static UI rule-of-thumb hint with no v1 equivalent text, unrelated to any computed
   report figure.
3. **"$91,661" (EV LCT threshold) flagged as "v2-only"** — a false positive from the diff
   script's own regex: v1's phrasing wraps the figure in parentheses as a citation
   ("...exceeds the EV Luxury Car Tax threshold ($91,661)"), which the script's
   negative-number heuristic (treats any parenthesized number as a signed accounting
   figure) misread as `-91661`, while v2's phrasing ("LCT threshold for this lease start
   date: $91,661") has no parentheses. Manually confirmed **both apps display the
   identical `$91,661` figure** — not a divergence, a diff-tooling artifact.

**The $449.25 loose end, settled:** re-checked the baseline scenario's BasicInformationReport
charging stats. Both apps now show the identical figures — Actual Charging Cost $765.00,
NL Claim Amount $820.50, Charging Delta $55.50, Net Charging Expense (after tax
reimbursement) $379.37 — matching field-for-field, including the label. (The $449.25 figure
from the first audit pass no longer appears in either app; it was evidently tied to inputs
or a formula that has since changed. There is no remaining discrepancy to explain.)

## Fixes applied

None. No real v2-only bug was found, so nothing needed a regression test or a code change.
`npx vitest run` in `calculator2/` remains 73/73 green, unchanged by this pass.

## Verdict

**Parity verified across the full 30-scenario matrix.** Every computed dollar and
percentage figure checked — across Summary, Details (all 8 sections), and Compare tabs,
covering FBT category tiers, lease terms 1-5y, deferral, luxury adjustment, the full
income-bracket sweep, the SG-loss toggle, and both comparators individually and combined —
matches exactly between v1 and v2. The only residual diffs are non-numeric UI-copy
differences (documented above) and a diff-tooling false positive, not calculation bugs.
This clears the way for CALCULATOR2_NOTES.md §3 item 3 (cut-over), pending the owner
go-ahead and the separate open items in §3 (items 2 and 4, and the maths-audit owner
decisions), which this pass did not touch.
